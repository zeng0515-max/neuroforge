# 多智能体协同代码生成与审查系统 — 技术设计文档

## 1. 项目概述

### 1.1 项目背景与痛点

大模型直接生成代码时存在三个工程层面的核心痛点。第一，**质量不稳定**：单次生成依赖模型概率采样，同一需求多次执行的结果差异显著，语法错误率与逻辑缺陷率波动大，无法满足工程交付的确定性要求。第二，**幻觉难以控制**：模型会编造不存在的 API、引用未导入的模块、生成签名不匹配的函数调用，这类问题在复杂业务逻辑场景下尤为突出，且单纯依赖模型自身审查无法根除。第三，**规范性缺失**：生成代码缺乏统一的命名约定、类型标注与文档结构，与团队工程规范脱节，直接可用率低，需大量人工修正。

现有方案通常采用"单次生成 + 人工修正"或"Prompt 工程优化"两条路径，前者将质量风险完全转嫁给开发者，后者则受限于模型推理能力的上限，均未从系统架构层面构建质量管控机制。

### 1.2 核心价值与定位

本系统的核心价值在于：将大模型从"一次性代码生成器"重构为"多角色协作的代码生产线"。通过引入智能体分工、AST 静态校验、LLM 语义审查、错误回流修复四重工程化机制，将代码质量的管控点从生成后的人工检查前移至生成过程中的自动化闭环，在不依赖更大参数模型的前提下，系统性降低语法错误率与幻觉率。

系统定位为**面向单模块/单文件代码生成场景的 AI 辅助开发工具**，聚焦 Python 语言的函数级、模块级代码生成与审查，不做全项目自动生成，不替代开发者决策，而是作为开发流程中的质量增强环节。

### 1.3 适用场景与边界

**适用场景：**
- 单功能模块/单文件 Python 代码生成（如工具函数、数据处理类、API 接口层）
- 已有代码的单元测试自动生成
- 代码审查与规范性检查
- 语法错误的自动检测与修复

**能力边界：**
- 不支持完整大型项目的自动生成与跨文件依赖管理
- 不支持多语言混合开发（架构已预留语言扩展接口）
- 不支持代码沙箱运行（当前仅做静态校验，运行时验证为后续扩展方向）
- 不支持实时交互式代码补全（定位为批量任务模式）

### 1.4 整体功能总览

系统围绕"需求输入 → 多智能体协作生成 → 双层校验 → 输出交付"的主链路，提供以下核心功能：

- **自然语言需求解析**：接收中文/英文自然语言描述，自动提取功能意图与约束条件
- **多智能体分工生成**：需求分析、代码生成、测试生成、代码审查、错误修复五个角色协同工作
- **AST 静态校验**：基于 Python `ast` 模块的语法结构验证，拦截未定义引用、签名不匹配等错误
- **LLM 语义审查**：独立审查智能体对生成代码进行逻辑正确性与规范性评估
- **错误回流修复**：校验失败的代码自动进入修复闭环，最多重试 N 轮后输出最终结果与错误报告
- **RAG 知识注入**：从向量知识库检索编码规范、API 文档、最佳实践，注入生成上下文
- **全链路日志追溯**：记录每个智能体的输入输出、校验结果、重试次数，支持任务级回溯

## 2. 系统整体架构

### 2.1 分层架构设计

系统采用四层架构，各层职责明确、单向依赖，上层通过标准接口调用下层能力，下层不感知上层业务逻辑。

**接入层（Access Layer）**：对外暴露 FastAPI 异步接口，负责请求接收、参数校验、用户认证、任务排队与结果返回。该层不包含任何业务逻辑，仅做协议转换与流量控制，解决多用户并发访问时的请求隔离与背压问题。

**调度层（Scheduling Layer）**：基于 LangGraph 构建的多智能体编排引擎，是系统的核心。维护全局 State，驱动需求分析、代码生成、测试生成、代码审查、错误修复五个智能体节点按编排图流转，控制循环次数与终止条件。该层解决的核心问题是：将一次性的大模型调用转化为可控的多步骤协作流程，使代码生成从"概率事件"变为"工程流程"。

**工具层（Tool Layer）**：基于 MCP（Model Context Protocol）思想设计的标准工具协议层。将 AST 解析、文件读写、向量检索、代码格式化等能力封装为标准工具，智能体通过统一接口按需调用。该层解决工具能力的硬编码耦合问题，使工具扩展不影响调度逻辑。

**数据层（Data Layer）**：包含 SQLite 关系数据库与 Chroma 向量数据库。SQLite 存储任务元数据、执行日志、生成结果；Chroma 存储编码规范、API 文档、历史代码等知识向量化后的 Embedding。该层解决状态持久化与知识复用问题。

### 2.2 核心业务流转全流程

用户提交自然语言需求后，系统执行以下完整链路：

1. **请求接入**：FastAPI 接收请求，生成唯一 `task_id`，初始化任务级 State，将任务投入异步队列
2. **需求分析**：需求分析智能体解析自然语言输入，提取功能意图、输入输出约束、异常处理要求，输出结构化需求规格
3. **知识检索**：RAG 模块根据需求关键词从 Chroma 检索相关编码规范与 API 文档，注入后续生成上下文
4. **代码生成**：代码生成智能体基于结构化需求与检索到的知识，生成初版代码
5. **AST 校验**：工具层对生成代码执行 `ast.parse` 静态分析，检测语法错误、未定义引用、导入缺失
6. **语义审查**：代码审查智能体对 AST 校验通过的代码执行逻辑正确性与规范性审查
7. **错误回流**：若 AST 校验或语义审查未通过，代码进入错误修复智能体，携带错误信息重新生成，回到步骤 5
8. **测试生成**：代码通过双层校验后，测试生成智能体生成单元测试
9. **结果输出**：最终代码、测试用例、执行日志、审查报告封装返回，全链路日志写入 SQLite

### 2.3 架构设计原则

**解耦**：调度层不直接调用具体工具实现，而是通过 MCP 协议定义的标准接口与工具层交互。新增工具只需注册到工具注册表，无需修改调度逻辑。数据层通过 Repository 模式封装，业务逻辑不直接操作数据库连接。

**可控**：所有智能体的循环次数、Token 消耗、超时时间均通过全局配置管控，不存在无限循环或资源耗尽风险。每轮校验结果与重试原因均记录到 State，支持人工介入与调试。

**可观测**：每个智能体节点的输入 Prompt、模型响应、执行耗时、Token 消耗均写入结构化日志。任务完成后可通过 `task_id` 查询完整执行链路，定位任意环节的输入输出。

**可扩展**：智能体角色通过 LangGraph 节点配置新增，工具通过 MCP 协议注册，模型通过抽象层切换厂商。核心调度逻辑不因任何单一组件的变更而修改。

## 3. 核心模块详细设计

### 3.1 多智能体调度模块

#### 全局 State 设计

全局 State 是 LangGraph 图在节点间传递的共享数据结构，采用 `TypedDict` 定义，字段按职责分为四类：

**任务元数据**：`task_id`（任务唯一标识）、`user_id`（用户标识）、`created_at`（创建时间）、`status`（任务状态：pending/running/completed/failed）

**需求与上下文**：`raw_requirement`（原始自然语言需求）、`structured_spec`（结构化需求规格，含功能描述、输入输出约束、异常处理要求）、`rag_context`（RAG 检索注入的规范与文档片段）

**生成产物**：`generated_code`（当前版本代码）、`test_code`（单元测试代码）、`review_report`（审查报告，含问题列表与评分）

**流程控制**：`iteration_count`（当前重试轮次）、`validation_errors`（AST 校验错误列表）、`review_issues`（语义审查问题列表）、`should_terminate`（终止标志）

State 设计的核心原则是**按需传递**：每个智能体节点只接收其工作所需字段的子集，而非全量 State。例如代码生成智能体接收 `structured_spec` + `rag_context` + `validation_errors`（若为重试），但不接收 `review_report`。这一设计直接解决了全量上下文传递导致的 Token 浪费与注意力稀释问题。

#### 五类智能体角色分工

| 智能体 | 输入 | 输出 | 职责边界 |
|--------|------|------|----------|
| 需求分析 Agent | `raw_requirement` | `structured_spec` | 解析自然语言，提取功能意图与约束，不生成代码 |
| 代码生成 Agent | `structured_spec` + `rag_context` + `validation_errors` | `generated_code` | 基于需求与校验反馈生成/修复代码，不做审查 |
| 测试生成 Agent | `generated_code` + `structured_spec` | `test_code` | 生成覆盖正常/边界/异常路径的单元测试 |
| 代码审查 Agent | `generated_code` + `rag_context` | `review_report` | 评估逻辑正确性与规范性，不修改代码 |
| 错误修复 Agent | `generated_code` + `validation_errors` + `review_issues` | `generated_code`（修复版） | 基于错误信息修复代码，不新增功能 |

角色分离解决的核心痛点是：单模型同时承担生成与审查时存在"自我确认偏差"——模型倾向于认可自己生成的代码，审查形同虚设。通过独立审查智能体配合独立 System Prompt，使审查视角与生成视角解耦。

#### LangGraph 节点编排与流转逻辑

系统采用 LangGraph 的 `StateGraph` 编排智能体流转，核心拓扑如下：

```
START → 需求分析 → RAG检索 → 代码生成 → AST校验
                                              │
                                    ┌───通过───┤───失败───┐
                                    │                   │
                                 语义审查          错误修复（iteration+1）
                                    │                   │
                           ┌──通过──┤──失败────────────┘
                           │
                        测试生成 → END
```

AST 校验与语义审查为条件分支节点：通过则进入下一阶段，失败则回流至错误修复节点。回流时携带具体的错误信息（AST 错误包含行号与错误类型，语义审查包含问题描述与修改建议），使修复智能体有针对性地修正而非全量重写。

#### 循环控制与终止机制

系统设置双重终止条件：

**硬边界**：最大重试次数 `MAX_ITERATIONS`（默认 3 次），无论错误是否修复完成，达到上限即终止并输出当前最优结果与错误报告。这一机制防止模型陷入"生成-报错-修复-再报错"的死循环，控制单任务的最大 Token 消耗。

**快速失败**：若 AST 校验连续两次报告相同错误（同一行号、同一错误类型），判定为模型无法修复该类错误，立即终止并标记为 `failed`，避免无效重试浪费资源。

### 3.2 双层校验模块

#### AST 静态语法校验

AST 校验基于 Python 标准库 `ast` 模块实现，不依赖大模型，执行成本为零。校验流程分三步：

1. **语法解析**：调用 `ast.parse(code)` 将代码字符串解析为抽象语法树，若解析失败则直接捕获 `SyntaxError`，记录行号与错误信息
2. **符号检查**：遍历 AST 节点，收集所有 `Import`/`ImportFrom` 语句的模块名与函数/类定义名，再遍历 `Call` 节点与 `Name` 节点，检查是否存在未导入或未定义的引用
3. **签名验证**：对函数调用节点，检查参数数量是否匹配函数定义的参数列表（含默认参数处理）

AST 校验解决的核心痛点是：大模型常生成语法正确但引用错误的代码（如调用了未导入的 `requests.get()`），这类问题通过模型自身审查难以发现，但通过 AST 符号表分析可以确定性拦截。

#### LLM 语义审查机制

语义审查由独立的代码审查智能体执行，采用与生成智能体不同的 System Prompt，审查维度包括：

- **逻辑正确性**：算法是否正确实现需求描述的功能，边界条件是否处理
- **异常处理**：是否覆盖常见异常路径（空输入、类型错误、越界访问）
- **规范性**：命名是否符合 PEP 8，函数是否有 docstring，类型标注是否完整

审查输出为结构化 JSON，包含 `pass`（是否通过）、`issues`（问题列表，每项含 `severity`/`description`/`suggestion`）、`score`（0-100 评分）。只有 `pass=true` 或所有 `issues` 的 `severity` 均为 `low` 时才进入下一阶段。

#### 错误回流与自动修复闭环

当 AST 校验或语义审查未通过时，系统将错误信息结构化后注入错误修复智能体的上下文。注入策略采用**错误分级**：

- **致命错误**（AST 语法错误、未定义引用）：必须修复，直接回流
- **严重问题**（逻辑缺陷、缺失异常处理）：必须修复，回流并附审查建议
- **建议项**（命名不规范、缺失 docstring）：记录但不阻塞流程，在最终报告中标注

修复智能体接收的 Prompt 包含原始代码、错误列表（带行号与类型）、修复建议，要求仅修改错误部分，不重写正常逻辑。这一约束防止修复过程中引入新的不一致。

### 3.3 MCP 标准工具层

#### 设计思想与解耦价值

传统方案中，智能体调用工具采用硬编码方式——在 Prompt 中直接描述工具用法，在代码中直接调用工具函数。这种模式导致三个问题：工具变更需修改调度代码、工具无法跨智能体复用、新增工具需重新编写调用逻辑。

本系统借鉴 MCP（Model Context Protocol）协议思想，将所有工具能力封装为标准接口。智能体通过统一的 `tool_call` 协议声明所需工具与参数，工具层解析后路由到具体实现。工具的注册、发现、调用均通过标准协议完成，调度层与工具实现完全解耦。

#### 核心工具清单

| 工具名称 | 功能 | 调用方 |
|----------|------|--------|
| `ast_validator` | 执行 AST 语法解析与符号检查 | 调度层（校验节点） |
| `code_formatter` | 基于 `black`/`autopep8` 格式化代码 | 代码生成 Agent |
| `vector_search` | 从 Chroma 检索相关知识片段 | RAG 模块 |
| `spec_parser` | 解析结构化需求规格 JSON | 需求分析 Agent |
| `test_runner` | 预留：执行单元测试并收集结果 | 测试生成 Agent（后续扩展） |

#### 统一调用入口设计

所有工具调用通过统一的 `ToolRegistry` 入口管理。智能体节点在需要调用工具时，向 Registry 提交工具名与参数，Registry 查找注册的实现并执行，返回标准化结果（`success`/`error`/`data`）。新增工具只需实现标准接口并注册到 Registry，无需修改任何智能体的 Prompt 或调度逻辑。

### 3.4 RAG 向量知识库模块

#### 知识库内容体系

向量知识库存储三类知识：

- **编码规范**：PEP 8 摘要、项目团队自定义命名约定、类型标注规范
- **API 文档**：Python 标准库常用模块 API 签名、第三方库（如 FastAPI、LangChain）的常用接口文档
- **最佳实践**：常见设计模式的 Python 实现示例、异常处理模板、单元测试编写规范

#### 检索注入时机与策略

RAG 检索在需求分析完成后、代码生成前执行。检索策略采用**关键词提取 + 语义检索**两阶段：首先从 `structured_spec` 中提取技术关键词（如"文件读取""异步""装饰器"），再用关键词生成查询向量，从 Chroma 检索 Top-K（默认 5）相关文档片段，注入代码生成智能体的上下文。

注入策略解决的核心痛点是：大模型的训练数据中包含大量过时或不规范的代码示例，直接生成时可能参考了已被废弃的 API 用法。通过 RAG 注入最新的规范文档与最佳实践，将生成过程锚定到可控的知识来源。

#### 向量库选型与切分方案

知识文档按语义边界切分：规范类文档按条款切分（每条 200-400 字），API 文档按函数/类切分（每个 API 独立成块），最佳实践按代码示例切分（含完整可运行代码块及其说明）。切分后使用 Embedding 模型向量化存入 Chroma，检索时余弦相似度排序。

### 3.5 持久化与日志模块

#### 核心数据表设计

**tasks 表**：`task_id`（PK）、`user_id`、`raw_requirement`、`status`、`created_at`、`completed_at`、`iteration_count`、`final_code`、`test_code`、`review_score`

**execution_logs 表**：`log_id`（PK）、`task_id`（FK）、`agent_role`（智能体角色）、`step_order`（执行序号）、`input_summary`（输入摘要）、`output_summary`（输出摘要）、`token_consumed`、`duration_ms`、`created_at`

**validation_results 表**：`result_id`（PK）、`task_id`（FK）、`iteration`（校验轮次）、`validation_type`（ast/semantic）、`passed`（是否通过）、`error_detail`（JSON 格式错误详情）

#### 全链路可追溯设计

每个智能体节点执行完毕后，将输入摘要、输出摘要、Token 消耗、执行耗时写入 `execution_logs` 表。通过 `task_id` 可查询完整执行链路，还原从需求输入到最终输出的每一步决策过程。这一设计解决了大模型应用常见的"黑盒问题"——当生成结果不符合预期时，开发者可定位到具体是哪个智能体、哪一轮校验出了问题。

### 3.6 接口层设计

#### 异步任务架构设计

由于多智能体协作生成代码耗时较长（单任务通常 30-120 秒），系统采用异步任务架构而非同步阻塞接口。用户提交请求后立即返回 `task_id`，后台异步执行生成流程，用户通过轮询接口或 SSE（Server-Sent Events）获取进度与结果。

异步架构解决的核心痛点是：同步接口在多用户并发时会阻塞 FastAPI 的工作线程池，导致后续请求超时。异步模式下，请求提交后立即释放线程，生成任务在独立的事件循环中执行，接口层可持续接收新请求。

#### 核心接口说明

| 接口 | 方法 | 功能 | 返回 |
|------|------|------|------|
| `/api/v1/tasks` | POST | 提交代码生成需求 | `task_id`、`status` |
| `/api/v1/tasks/{task_id}` | GET | 查询任务状态与结果 | `status`、`code`、`test`、`logs` |
| `/api/v1/tasks/{task_id}/stream` | GET (SSE) | 实时推送任务执行进度 | SSE 事件流 |
| `/api/v1/tasks/{task_id}/logs` | GET | 查询全链路执行日志 | `execution_logs` 列表 |

## 4. 关键技术方案与痛点解决

### 4.1 多用户并发稳定性方案

#### 任务级状态隔离机制

每个任务拥有独立的 State 实例，智能体节点的执行上下文通过 `task_id` 隔离。LangGraph 图在每次任务执行时创建新的 State 副本，不同任务之间不共享可变状态。这一设计防止并发任务之间因 State 污染导致生成结果串扰。

#### SQLite 并发写优化方案

SQLite 默认使用文件级锁，多线程并发写入时会触发 `database is locked` 错误。系统采用三项优化：

- **WAL 模式**：开启 Write-Ahead Logging，读写分离，读操作不阻塞写操作
- **写队列序列化**：所有写操作通过 `asyncio.Lock` 序列化，避免并发写入冲突
- **连接池复用**：使用单连接 + 线程安全队列，减少连接创建开销

该方案在【待填充：并发用户数】并发场景下，写入成功率达【待填充：写入成功率】，平均写入延迟【待填充：写入延迟】ms。

#### 全局并发控制与排队机制

系统设置全局信号量 `asyncio.Semaphore`，限制同时执行的最大任务数（默认 5）。超出限制的请求进入 FIFO 队列等待，避免资源耗尽导致所有任务超时。队列位置与预计等待时间通过 SSE 推送给客户端。

#### 两级超时控制与异常兜底

- **节点级超时**：单个智能体节点执行超过 60 秒即终止，记录超时日志，该轮判定为失败
- **任务级超时**：整个任务执行超过 300 秒即终止，输出当前已完成的最优结果与超时报告

超时机制防止模型 API 响应慢或网络抖动导致任务永久挂起，保障系统整体可用性。

### 4.2 幻觉与成本控制方案

#### 结构化上下文按需传递

如 3.1 节所述，每个智能体只接收其工作所需字段的子集。全量 State 包含原始需求、结构化规格、RAG 上下文、生成代码、测试代码、审查报告、错误列表等十余个字段，若全量传递给每个智能体，单次调用的 Prompt Token 消耗将达【待填充：全量传递Token数】，而按需传递可降至【待填充：按需传递Token数】，降幅【待填充：降幅百分比】。

#### 硬边界控制与无效循环终止

通过 `MAX_ITERATIONS` 硬上限与"连续相同错误快速失败"机制，控制单任务最大重试次数。实测中，【待填充：百分比】%的任务在 1-2 轮内通过校验，极少任务触发 3 轮上限，无效 Token 消耗得到有效控制。

#### 错误分级处理与快速失败策略

AST 校验错误为致命级，必须修复；语义审查中 `severity=high` 的问题必须修复，`severity=medium` 记录但允许通过（附警告），`severity=low` 仅记录。分级策略避免了因格式规范等低优先级问题反复重试，缩短了任务执行链路。

#### 模型分级调度与缓存机制

- **分级调度**：需求分析与代码审查使用较强模型（如【待填充：强模型名称】），代码生成与错误修复使用标准模型（如【待填充：标准模型名称】），测试生成使用轻量模型（如【待填充：轻量模型名称】），在质量与成本间取平衡
- **缓存机制**：对相同需求的 RAG 检索结果与需求分析结果做 LRU 缓存，避免重复调用

### 4.3 模型接入抽象方案

#### 统一模型调用层设计

系统通过 `ModelAdapter` 抽象层封装所有大模型调用。上层智能体通过 `model.generate(prompt, **kwargs)` 统一接口调用，不感知底层模型厂商。`ModelAdapter` 负责将统一参数转换为各厂商 API 的具体请求格式，并将响应统一为标准结构（`content`/`usage`/`finish_reason`）。

#### 多厂商 API 兼容与私有化部署适配

当前已适配【待填充：已适配模型列表】，通过继承 `BaseModelAdapter` 实现新厂商适配仅需覆盖 `_format_request` 与 `_parse_response` 两个方法。对于私有化部署的模型，只需配置本地推理服务地址即可接入，无需修改业务代码。

#### 重试、超时、限流统一封装

`ModelAdapter` 内置三项稳定性机制：

- **指数退避重试**：API 调用失败时按 1s/2s/4s 间隔重试，最多 3 次，仅对网络错误与 5xx 状态码重试
- **请求超时**：单次 API 调用超时 60 秒，超时后抛出 `ModelTimeoutError`
- **令牌限流**：基于 Token Bucket 算法限制每分钟最大请求数与 Token 消耗量，防止突发流量打满模型 API 配额

## 5. 技术选型说明

### LangGraph（对比 AutoGen）

选用 LangGraph 的核心理由是**状态可控性**。LangGraph 基于显式 StateGraph 定义节点与边，全局 State 的字段类型与流转路径在代码中清晰可见，开发者可精确控制每个节点的输入输出与条件分支。AutoGen 的对话式编排（conversation-driven）更灵活，但状态在多轮对话中隐式传递，难以做细粒度的字段级控制与按需传递，且调试时缺乏完整的 State 快照。

对于需要工程化质量管控的系统，显式的状态图比灵活的对话编排更适合——每一次状态变更都可追溯、可审计、可单元测试。

### Chroma（对比 Milvus、FAISS）

Chroma 的核心优势是**轻量嵌入式部署**。系统定位为单模块代码生成工具，不需要分布式向量检索能力，Chroma 以嵌入式模式运行，无需独立部署数据库服务，与 SQLite 一起构成零运维的本地数据层。

Milvus 适合亿级向量的分布式检索场景，但部署成本高（需 etcd + MinIO + Milvus 三组件），对本项目过重。FAISS 是库而非数据库，缺乏持久化与元数据过滤能力，需要自行管理向量与文档的映射关系，增加工程负担。

### SQLite（对比 PostgreSQL）

SQLite 的选型基于三点考量。第一，**零运维**：无需安装数据库服务，单文件存储，适合工具型应用。第二，**足够性能**：本系统的写入场景以任务日志为主，QPS 在个位数级别，SQLite WAL 模式完全胜任。第三，**可移植**：数据库文件随项目目录迁移，方便演示与部署。

PostgreSQL 在并发写入、复杂查询、数据量扩展方面更强，但本项目的数据规模与并发量未达到需要独立数据库服务的阈值。架构上通过 Repository 模式封装数据访问，后续若需迁移至 PostgreSQL，仅需替换 Repository 实现。

### MCP 协议思想（对比硬编码工具调用）

MCP 协议思想的核心价值是**工具层的独立演进**。硬编码方式下，工具变更需修改调用方的代码与 Prompt，测试时需端到端验证。采用 MCP 思想后，工具通过标准协议注册与发现，调用方仅依赖接口契约，工具实现可独立开发、独立测试、独立替换。

在本系统中，AST 校验工具从最初的"仅语法解析"迭代到"符号检查 + 签名验证"，整个过程未修改任何智能体的代码或 Prompt，仅更新了工具实现——这是解耦带来的直接工程收益。

### 异步任务架构（对比同步接口）

同步接口在多智能体场景下的致命问题是**线程阻塞**。单任务执行需 30-120 秒，FastAPI 默认线程池仅 40 个工作线程，4-5 个并发任务即可耗尽线程池，导致后续请求排队直至超时。

异步架构下，任务提交后立即返回 `task_id`，生成流程在事件循环中异步执行，接口层可持续接收新请求。用户通过轮询或 SSE 获取结果，体验上从"等待 60 秒"变为"即时提交 + 进度推送"。

## 8. 项目亮点

**多智能体分工替代单次生成**：将代码生成从"一次调用"重构为"需求分析 → 生成 → 校验 → 审查 → 修复"的多角色协作流水线，每个角色有明确的输入输出与职责边界，使生成过程从概率事件变为可控工程流程。独立审查智能体消除了单模型的自我确认偏差。

**双层校验构建质量闭环**：AST 静态校验零成本拦截语法与引用错误，LLM 语义审查覆盖逻辑正确性与规范性，两层校验互补——前者确定性拦截硬错误，后者处理语义级问题。错误回流机制将校验从"检查"升级为"修复闭环"。

**工程化并发与成本管控**：任务级状态隔离、SQLite WAL 优化、信号量并发控制、两级超时兜底，构成多用户并发场景的稳定性保障。按需上下文传递、硬边界终止、错误分级处理、模型分级调度，在保障质量的前提下控制 Token 消耗与执行成本。

**全链路可观测设计**：每个智能体的输入输出、Token 消耗、执行耗时均结构化持久化，通过 `task_id` 可还原完整决策链路。这解决了大模型应用的"黑盒问题"，使系统具备可调试性与可审计性。

**MCP 思想的工具层解耦**：工具能力通过标准协议注册与调用，调度逻辑不耦合工具实现。工具可独立开发、测试、替换，支持横向扩展新工具而不影响现有流程。

## 9. 后续优化方向

### 质量维度

- **沙箱运行验证**：引入 Docker 容器执行生成的代码与单元测试，从静态校验升级为运行时验证，拦截逻辑正确但运行时崩溃的代码
- **测试覆盖率分析**：集成 `coverage.py`，对生成的单元测试计算覆盖率，低于阈值的测试自动补充用例
- **审查模型微调**：积累审查日志中的高质量反馈数据，微调轻量审查模型，降低审查环节的 Token 成本

### 工程维度

- **分布式任务调度**：当前单机信号量限制并发，后续可引入 Celery 或 Redis 队列实现多机分布式调度，支撑更高并发量
- **数据库迁移**：当任务量增长到万级以上时，将 SQLite 迁移至 PostgreSQL，利用其原生并发能力与索引优化
- **监控告警**：接入 Prometheus + Grafana，监控任务成功率、平均耗时、Token 消耗趋势，异常时自动告警

### 功能维度

- **多语言支持**：扩展 AST 校验器支持 JavaScript/TypeScript（基于 `esprima`/`typescript-estree`），实现多语言代码生成
- **增量代码生成**：支持基于已有代码库的增量生成，而非每次全量生成，适配实际开发中的迭代场景
- **IDE 插件集成**：将系统封装为 VS Code 插件，在编辑器内直接调用生成与审查能力，降低使用门槛

## 10. 总结

本项目以"工程化质量管控"为核心思路，通过多智能体分工协作、双层校验闭环、MCP 工具解耦、全链路可观测四大机制，系统性地解决了大模型直接生成代码时的质量不稳定、幻觉多、规范性不足三个痛点。系统的价值不在于提升单次大模型调用的能力，而在于通过架构设计将不可控的概率生成转化为可控的工程流程——这正是大模型应用从"Demo 可用"走向"工程可用"的关键一步。

技术沉淀方面，项目完整实践了 LangGraph 状态图编排、RAG 知识注入、MCP 工具协议、异步任务架构、并发控制等大模型应用工程化的核心模式，为后续更复杂的 Agent 系统积累了可复用的架构经验。
